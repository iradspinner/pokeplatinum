# Platinum Oxide: Hardlove Gold engine-expansion integration into Pokemon Platinum

Design document, v0.61 (2026-10-03). This file is written for Claude to work from. Read it in full at the start of every session, then read `docs/oxide/tracker.md`, then act. Facts and rules live here; status lives in the tracker; the encounter tool's own status and findings live in `docs/oxide/encounter-tool-build-plan.md`.

## 1. What this project is

Port the engine-expansion elements of Hardlove Gold (a HeartGold hack, v0.6.9) into Pokemon Platinum, built from the pokeplatinum decomp (section 4), keeping the edits Ian made earlier to a DSPRE-edited Platinum ROM (the base ROM, section 2).

Two reasons, in Ian's words: to find out whether it can be done at all, and to work inside a game he knows far better than HeartGold.

This is a hobby project. No QA gate, no release schedule. The bar is "works in an emulator and Ian is happy with it."

### Size of the gap, by the numbers

Hardlove's personal struct is hg-engine's `SpeciesData`, not Platinum's, and its index for Gen 5+ species is National Dex number + 50. Every donor layout is recorded in `docs/oxide/donor-tables.md` and `donor-move-tables.md`, read out of the ROM itself, and read through `tools/oxide/donor.py` (the `read-donor` skill); those are the reference for reading donor records.

### Filesystem layout differences (from `path_order.txt`)

Platinum keeps its data under named paths (`/poketool/personal`, `/poketool/waza`, `/fielddata/encountdata`, `/msgdata`, `/battle`, `/wazaeffect`, and so on). HeartGold (and therefore Hardlove) collapses almost everything into `/a/0/x/y` numbered NARCs. Nothing can be copied across by path name; every table has to be matched by content and purpose, then converted.

Platinum's extraction also carries `encounterExtended`, `tradeData`, `trainerParty`, `trainerTextTable`, `pokemonSpriteOffsets`, `pokeHeight` and `battleBg/battleObj` folders that the Hardlove extraction does not, and Hardlove's has `interiorBuildingModels`. Some of that is a DSPRE-version difference rather than a game difference; confirm before relying on it.

### How hg-engine (and therefore Hardlove) is put together

hg-engine is a patch kit applied to a vanilla US HeartGold ROM, not a rebuilt game. Compiled C goes into new overlays 129..151 (129 is loaded at boot as a permanent arm9 extension); ~1,370 lines of hook/repoint/byte-replacement lists and ~3,200 lines of armips patches edit the vanilla arm9 and overlays at fixed addresses; ~40 NARCs are regenerated from source data. Hardlove's extraction shows exactly this (overlays 129..151 at hg-engine's load addresses, hg-engine's species and move numbering). Full detail: `docs/oxide/phase1-hg-engine-survey.md`.

Consequence: none of hg-engine's addresses exist in Platinum. Porting means re-targeting the same design onto Platinum's binaries (or rebuilding from Platinum's decomp), not copying files.

### Tooling already built (Hardlove side)

`romtool\hardlove.py` in the hub folder is an older HeartGold-shaped reader with a proven NARC round trip. The repo does not use it: `tools/oxide/import_base_rom.py` has its own NDS and NARC readers for the Platinum side, and `tools/oxide/donor.py` reads the donor (the `read-donor` skill).

## 4. Approach: DECIDED. Approach C, build from the pokeplatinum decomp (Ian, 2026-09-15)

The project's ROM is built from source in Ian's fork of `pret/pokeplatinum`. Claude edits the source tree, commits and pushes from the WSL2 checkout or a cloud session, the ROM is built (on GitHub while this box's CPU is degraded; `CLAUDE.md`, Build), and Ian plays the result (setup in `docs/oxide/setup-fork-and-wsl2.md`). hg-engine's source is the reference implementation for each feature; Hardlove's tables are the content source. The base ROM (section 2) is a reference for re-creating Ian's earlier edits, not the thing being patched; its inventory is `docs/oxide/phase3-base-rom-inventory.md`, and Phase 3 (the tracker and its archive) records how each of those edits was carried over.

### How this was decided

Phase 1 (2026-09-15) established that every scoped element is code plus data: type, ability, move and species expansion each depend on hooks and byte patches into HeartGold's arm9 and battle overlay, plus regenerated NARCs, so nothing in scope is achievable at the data layer alone (`docs/oxide/phase1-hg-engine-survey.md` sections 1 and 3). That ruled out approach A (data-layer only, DSPRE and scripts). Phase 2 compared the remaining two, (B) re-targeting the hg-engine patch kit onto Platinum from plat-engine's skeleton and (C) building from the pokeplatinum decomp (the comparison is `docs/oxide/phase2-approach-breakdown.md` in git history), and recommended C after verifying that the decomp is 100% C, builds a byte-matching Rev 1 ROM in about 8 minutes, and is actively maintained. Ian approved C the same day.

The facts that carried the decision, kept here because they still shape Phase 4: hg-engine is a patch kit over vanilla HeartGold, so its addresses are useless in Platinum and only its design and C carry over; plat-engine is the same patch-kit design for Platinum, dormant since 2023 and roughly 10% along, useful only as a second address reference; pokeplatinum is the address oracle and the source base, and no public decomp-based Platinum hack has done a dex, type or ability expansion, so that part is new ground.

## 8. Findings log

Durable facts discovered during work, newest last. Each entry: date, what was checked, what was found. Track agents only append. An entry may be deleted once its lesson lives in a working rule, a skill, a tool or a status home and the entry no longer changes what a fresh agent would do; such deletions are made in a docs pass with every track paused, because `integrate.sh` resolves a conflict in this section by keeping both sides, which would resurrect a deleted entry next to a concurrent append.

- 2026-09-21: The whiteout hang was a script-alignment defect, and it teaches two things. First, the ARM9 drops the low address bit on halfword loads, and field-script movement blocks are arrays of halfword commands, so a movement block at an odd offset reads as garbage actions; vanilla puts `.balign 4, 0` before every movement label for exactly this reason, and the bulk-generated scripts do not, because they reproduce the base ROM's own padding byte for byte. That is safe only while a generated file keeps its length; the Repel fix shortened `scripts_common` by 15 bytes and broke every movement block behind the edit. Second, the Windows melonDS 1.1 GDB stub is usable from WSL2 under mirrored networking but with two limits: one client per emulator session (a dropped client wedges the stub until restart) and no servicing while the CPU runs, so a target cannot be interrupted on demand; what works is connecting at the startup break, planting breakpoints, continuing, and reading memory or single-stepping at each stop. `tools/oxide/live_watch.py` does that with arm-on, hold-at, burst, auto-command and function-level trace modes, and the sequence that found this bug (heartbeat breakpoints to prove the main loop ran, then stage breakpoints to find the frame, then object and pointer reads at the script's movement commands) is a reusable method for any freeze.
- 2026-09-21 and 2026-09-22: Docs passes. Entries were deleted from this log under the rule in the paragraph above, thirty on 2026-09-21 and three on 2026-09-22, each after checking that its lesson lives in a working rule, a skill, a tool or a status home, and on 2026-09-22 three entries on the Python fault were merged into one; each pass's commit names every deleted entry and where its lesson now lives. The method is the `/docs-pass` command.
- 2026-09-21: Auditing element 3's remaining caps found one live defect and one ceiling. **The defect:** `Pokemon_GetFormNarcIndex` in `src/pokemon.c` hardcoded 496, 499, 501, 502 and 503 as the `pl_personal` and `wotbl` members that hold the twelve alternate-form records. Those two archives put the form records after every species and after EGG and BAD_EGG, so inserting 159 species moved them to 655 onward and the five literals began reading new species' records instead. The three Deoxys forms, both Wormadam forms, Giratina Origin, Shaymin Sky and the five Rotom forms would every one of them have had the wrong base stats, types, abilities and level-up learnset. They now derive as `MAX_SPECIES + n` in `include/constants/forms.h`, written beside the `MOVESET_FORM_*` block, which derives as `NATIONAL_DEX_COUNT + n` because the tutor table it indexes has no egg entries; the two bases differ by exactly those two eggs and both are now written down. Verified twice: against the pinned vanilla build, where `MAX_SPECIES + 1` is 496 and the new expression reproduces the old literals exactly, and against the current build, where 655, 658, 660, 661 and 662 hold the expected form stats. **The general rule: a literal that happens to equal a derived constant is a latent bug from the moment the constant moves**, and the species insertion moved four numbering schemes at once (species ids, dex numbers, form-record indices, tutor-table indices), so a bare number near a species-indexed table earns a check rather than a glance. Everything else audited derives correctly and needed no change, including the `zukan_enc_platinum` stride, whose archive is generated at `4 + MAX_SPECIES * 10` and already holds 6,544 members. **The ceiling:** `BattleHallWinRecords` is three `u16[MAX_SPECIES]` arrays and lives in the *extra* save table, whose entries sit at fixed sector numbers with no bounds check at all, `SaveDataExtra_Save` writing its bytes straight at `blockID * SAVE_SECTOR_SIZE`. Its entry is one sector wide, and at 654 species the struct plus footer is 3,948 of the 4,096 bytes, which caps `MAX_SPECIES` at 679 before it overruns the stored battle recordings. Nothing to do at 654; recorded in `docs/oxide/save-layout.md` so a later species addition moves the entry rather than growing into its neighbour.
- 2026-09-21: Footprints are a Generation 4 feature, which settles one of element 3's fill-in items rather than leaving it open. Black and White dropped the footprint from the Pokedex and Black 2 has no archive of them, checked by scanning every NARC in the ROM for one of the right shape. Every one of the 159 new species is Generation 5 or later, so **no game has ever drawn a footprint for any of them** and `"has": false` is the correct value, not a gap, for 147 of them. The 12 that can be done properly are the regional forms, the megas and the cross-gen evolutions, which are the same creature as a Generation 4 native and take that native's print. Two of those, Galarian Weezing and Mega Gyarados, inherit `false`, because Weezing and Gyarados have no feet. The general shape of this: before filling a gap with invented data, check whether the gap is the data. The same question is worth asking of the dex size-comparison scales, which are still defaults.
- 2026-09-21: The level-up learnset packing was a second instance of the pattern element 3's caps audit found, and worth naming as a pattern rather than a bug. Vanilla stored an entry as one `u16` of `move:9 / level:7`, and four readers in `src/pokemon.c` plus `move_reminder_data.c` each did the `& 0xFE00` and `& 0x1FF` arithmetic by hand rather than going through the struct, so the format was written down in six places and enforced in none. Widening it to two halfwords was therefore not one edit but six, and the only reason all six were found is that the struct existed to grep for. **Where a bit-packed format is read by hand at each call site, the struct is documentation rather than a contract, and widening it is a search problem.** Two smaller facts from the same change: `LEARNSET_SENTINEL_ENTRY` and `LEARNSET_ALL_SLOTS_FILLED` are both `0xFFFF` and mean entirely different things, one ending a learnset and the other a return code from `Pokemon_AddMove`, and vanilla's `Pokemon_LoadLevelUpMoveIdsOf` terminated on the wrong one and worked only by that coincidence. And the way to prove a format widening faithful is to teach the verifier both layouts and compare decoded values rather than bytes, which is what element 2 did for the species record and what `verify_narcs.py` now does for `wotbl`: all 508 reference learnsets decode identically, which no byte comparison could have said.
- 2026-09-21: Widening a packed table in this decomp moves code addresses, and the right way to prove that harmless is not to read the bytes. The learnset widening was checked by building the previous commit in a throwaway worktree and diffing both ROMs: **every file in the ROM is byte-identical except `poketool/personal/wotbl.narc`**, 25,004 to 43,272 bytes, 462 files both sides with none added or removed. The symbol tables hold 44,515 symbols both sides, again none added or removed, and **exactly four symbols changed size**, which are the four rewritten functions. The arm9 image shrank 64 bytes, so `SDK_MAIN_ARENA_LO` and `SDK_SECTION_ARENA_START` moved down by 64 and the heap is 64 bytes larger; the dominant literal-pool delta across every overlay is the same -64, in 19,519 of 19,813 cases. Byte-classifying the rest was abandoned deliberately: after a relink nearly every function that calls a moved function differs by a branch offset, so "only X changed" is not provable from bytes and the symbol-level evidence is what carries it. **The property that matters is not whether addresses moved but whether anything depends on one**, and the only absolute addresses in the whole source are three NDS hardware constants in `src/boot.c`, none in the image region. This is the structural difference from hg-engine, where a shift genuinely is a bug because it patches absolute addresses; here the linker resolves everything. The one real hazard of the change class, a whole-member read into a fixed buffer, was checked separately: the largest `wotbl` member is 120 bytes against a 140-byte buffer, and both derive from `MAX_LEARNSET_ENTRIES`, so they cannot drift apart.
- 2026-09-22: Easy Chat word ids are a running total across text banks, which makes every text bank that holds names a save-layout concern. `include/applications/easy_chat/defs.h` defines `MOVE_WORD` as starting where the species names stop, `TYPE_WORD` where the move names stop, and so on through abilities, trainer words, greetings and the rest, so **adding names to an early group renumbers every later group**. The ids are stored: `EasyChatSentence.words[2]` is saved in `Mail`, twenty in the mailbox plus one per Pokemon holding mail, and in the player's trainer messages. Elements 2, 3 and 4 have each done it, 195 abilities then 161 species then 455 moves, taking the word count from 1,494 to 2,305 and `TYPE_WORD(0)` from 962 to 1,578, and only element 4 noticed. Nothing breaks at this size, because the ids are `u16` and `EASY_CHAT_WORD_COUNT` derives from the same running total so the arrays grew with it; an old save simply reads different words in its mail. This is a second instance of the rule from 2026-09-21: the trigger is not "did I edit a save struct" but "did anything sized by a constant I changed end up in the save", and **a text bank's entry count is exactly that kind of constant**.
- 2026-09-22: A verification gate that defers a check is a gate with a hole in it, and the hole is worth closing at the moment it opens rather than later. `verify_narcs --text` compares a text bank message for message against the reference ROM, but skips any bank whose entry count changed, because there is nothing to line up. Phase 4 has grown 25 banks that way, species names in element 3 and the four move banks in element 4, so by element 4 a quarter of the deferred list was unchecked and nothing would have caught a native move name or species name coming out wrong. The fix is the same idea as the move table's: **a bank that grew still has to match on the entries it shares with the reference**, so compare the prefix and report it separately. All 25 agree, which is the first evidence that elements 2 and 3 did not disturb the text they appended to either.
- 2026-09-22 and 2026-09-23: **hg-engine's battle scripts and Platinum's are the same language**, and converting them taught two things; the rules the converter learned (the shared numberings, renames that must agree on value and on opcode, hg-engine's own defects in `FIXES`, Protect as move data in `SETTLED`) are in `tools/oxide/convert_battle_scripts.py`. - 2026-09-22: A trainer Pokemon's nature is not stored anywhere, and the way the game rolls it makes the IV scale and the nature one lever. `TrainerData_BuildParty` seeds the LCRNG with **IV scale + level + species + trainer id, a single sum**, steps it once per trainer-class id, and the nature is the resulting personality mod 25. - 2026-10-03: **A trainer party keeps its held items and moves only if its first member names them.** The trainer packer (`tools/dataproc/src/trainerproc.c`, around line 186) reads the first party member to choose the party's data type: items are packed only if that member's `item` is a string, and moves only if its `moves` is an array. A party whose first member has `"item": null` loses every member's item in the built game, silently. Give the first member `"item": "ITEM_NONE"` when it holds nothing and a later member holds something, and the same for moves. Found by the Scoring Agent in the Kaizo study's worked examples; 13 of the study's 20 combed Roark trainers had it.
- 2026-09-29: **What a dungeon's tiles say about how it is walked, and four facts the gauntlets rest on** (`main-gauntlets`). A Rock Climb wall is a tile with the collision bit and a ROCK_CLIMB behaviour, climbed along its axis; a bridge's tiles are both its deck and the floor under it, told apart by whether the player stepped on from a bridge end; a ledge is taken only in its direction. A flood fill that ignores these joins a cave's levels into one, as it did on Victory Road 1F. `tools/oxide/mapreach.py` models all three and prints each map's pockets with their warps and trainers. Read that way, Victory Road 1F runs from its entrance to its exit alone, with 2F and B1F as detours off it, and Galactic HQ is walked from B2F up, since the warehouse leads into B2F. The four facts: a script's `Warp` starts the map change with warp id -1, so it never looks like arriving through a warp; a coord event's script number may be any global script id (10000 and up is the field moves archive), not only its own map's; `CallCommonScript` starts any archive's script with that archive's text bank; and a normal continue from a save does not run `FieldMapChange_UpdateGameData`, while every warp, whiteout and scripted warp does.
