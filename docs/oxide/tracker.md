Short version: 184 maps are touched (65 script+events, 26 script-only, 93 events-only), and the unit of work is a map done across events, script and text together, because a new object event is an NPC needing a script to run and text to say.

**Next steps, in order:**

1. **Movement-block decoder** in `tools/oxide/scriptdis.py`. `ApplyMovement` points at a separate encoding the disassembler does not read yet; 2,222 references in vanilla, 2,217 in the base ROM. Validate it the way the rest was: every referenced block accounted for, nothing colliding with decoded code.
2. **Emit `.s` text** - labels for entries and jump targets, symbolic operands (text-bank entries, `LOCALID_*`, flags, vars, items, species), matching the house style of `res/field/scripts/*.s`.
3. **The true round trip.** Reassemble through the real build and require byte-identical output over all 1,124 vanilla files. A clean walk proves the operand widths; it does not prove the emitted text reassembles.
4. **One small map end to end** (events + script + text), built and checked in the emulator. Best candidates: `oreburgh_city_middle_house`, `floaroma_meadow_house`, `sandgem_town_house`, `solaceon_town_northeast_house`.
5. **The 93 events-only maps**, then the rest largest-last. Before relying on the "73 of them are safe alone" figure, resolve each map's script file through its header's `scriptsArchiveID` rather than by name; at least two Mt Coronet maps do not line up by name.

**To confirm the state after a restart**, from the repo root:

```
make rom
python3 tools/oxide/import_base_rom.py --base ~/roms/base.nds --vanilla ~/roms/vanilla.nds --dry-run   # every count should be 0
python3 tools/oxide/verify_narcs.py --built build/pokeplatinum.us.nds --ref ~/roms/base.nds
python3 tools/oxide/verify_narcs.py --built build/pokeplatinum.us.nds --ref ~/roms/base.nds --encounters
python3 tools/oxide/verify_narcs.py --built build/pokeplatinum.us.nds --ref ~/roms/base.nds --text
python3 tools/oxide/verify_narcs.py --built build/pokeplatinum.us.nds --ref ~/roms/base.nds --map-headers
python3 tools/oxide/scriptdis.py --rom ~/roms/vanilla.nds --verify
python3 tools/oxide/scriptdis.py --rom ~/roms/base.nds --verify --base-rom
```

The importer is idempotent, so a non-zero count means something moved. Both `scriptdis` runs should report 574 files walked, 0 failed, 550 init scripts read and 0 movement-target collisions.

Two things the plan pins down that the design doc does not. First, the calibration corpus is on `main`, not in the working tree — the `oxide` branch's `res/field/encounters/` holds the base ROM's rewritten tables, so every "does this reproduce vanilla" check has to read `git show main:...` and the CLI needs `--ref` from day one. Second, the design doc's R1 (slot levels non-decreasing with slot index, error severity, and acceptance criterion 6 expects vanilla to pass it) is contradicted by the files: only 20 of 171 vanilla land tables are monotonic by slot index, vanilla Route 201 being the clean counter-example with its 1% slots at the table's minimum level. The ladder is real but it is a correlation, not an ordering — rarity-vs-level Spearman medians +0.68 and is positive on 88% of tables, and 136 of 171 tables still have exactly four distinct levels. - 2026-09-20: Encounter tool M2 (the analysis engine) is done, 23/23. `tools/oxide/encounters/analysis.py` holds all of design-doc section 6 as pure functions, rate-array-agnostic so water and fishing tables are later a config change; `cli report` prints them per-area or game-wide. The repel model agrees with a simulation of the game's own `RepelPreventsEncounter` to within 2.62 sigma over 292 comparisons, checked against sampling error rather than a flat tolerance. Vanilla reproduces the survey on every headline number: median HHI 0.275, p10-p90 0.173-0.428, spread 2.48x, 71 distinct signatures, 5 species per table, top slot 40%, early 0.373 to late 0.275, the ladder +0/+1/+1/+1/+2/+2/+2/+2/+2/+2/+3/+3, and real tails on 6% of tables. Two ambiguous definitions were pinned by measurement: rarest-species uplift must break ties toward the best available uplift (3.33x on 83%, where the 83% reproduces the survey's "rarest survives" column exactly; tie-by-name gives 2.86x on 80%), and the survey's headline 5.0x is not the rarest-species number at all but the best manip available to any species on the table (5.00x working on 88%, both exact) - so both statistics now ship as `uplift_on_rarest` and `best_uplift`. One survey number does not reproduce and R6 is calibrated on it: design doc 2.6 says 8% of vanilla repel tiers collapse to a single species, but vanilla measures 24% of rungs with no variant getting near 8%. The base ROM's tables measure 7%, which suggests that figure may have been computed against a working tree that already held them rather than against vanilla - a hypothesis, not a finding, but R6's threshold needs re-deriving from vanilla's 24% before M3 enforces it, the same way R1's did. Running `report` against the working tree is the first real payoff and confirms two of Ian's three complaints as measured facts: spread 2.14x (fails R8's 2.2) and 0.26 signatures per table (fails R9's 0.35) are complaint 3, and the early-to-late arc running backwards at 0.143 to 0.230 is complaint 2, the same inversion the survey found in Elite Redux and Inclement Emerald. Complaint 1 is refuted in its obvious form and confirmed in Ian's: uplift is 6.67x working on 99%, better than vanilla, but 67% of tables carry an exclusive 1-2% tail against vanilla's 6%, so a repel resolves to one guaranteed species instead of a smaller richer pool - exactly the "binary logic" Ian objected to. The fix is fewer exclusive tails and more re-weighting, not more uplift. Next: M3, the linter.
